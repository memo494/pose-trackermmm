## Scope decision (lead; for the owner to read, not to wait for)
ARCHITECTURE §12 gives M1 five parts. This session does the two the owner asked for and M3/M4 need, as **M1a**:
1. **Rectangular model inputs** end to end (import, engine, HUD, diagnostics) and rectangular models to download.
2. **Timing statistics** in the diagnostics (p50/p95 per stage, result age, thermal state).

Moved to **M1b** (after M4, its own session): the golden decode test with raw-output goldens, the pure-Kotlin
decoder, the benchmark screen with CSV and soak mode, and the choice of a bundled landscape model. Reasons: the
decoder may only be rewritten behind raw-output goldens, which need a new Python export run (slow, protected
files); the benchmark screen is a tool, while M3 and M4 are what the owner sees.

Already true, no task: **one-thread LiteRT** (M0b: `LiteRtPoseDetector` is created, used and closed on the
capture thread and throws from any other thread).

**Sizes are written WIDTHxHEIGHT everywhere** (HUD, `summary.txt`, file names, `--sizes`), like the capture
geometry log (`capture 1356x610`). A square model keeps the single number (`640`).

Why these candidates: M0d (video-area crop) stays parked, so the model sees the whole landscape screen
(1356x610, aspect 2.22). Content scale today (640²) is 0.472. `640x288` has the same scale at about two thirds
of the time; `832x384` gives 0.614 (1.3x) at about 85 % of the time; `960x448` gives 0.708 (1.5x) at about the
same time. In portrait a landscape model is worse than any square one (scale 0.28): it is a model for
landscape, and the checklist says so. Per-orientation model choice is M1b.

## Knowledge note (no consult used; lead on Fable 5.2 checked the source)
LiteRT Kotlin `TensorBuffer.readFloat()` allocates a new `FloatArray` on every call (JNI `NewFloatArray` in
`litert_tensor_buffer_jni.cc`; `TensorBuffer.kt` has no read-into overload). The output readback of 300x57
floats (68 KB per frame) can therefore not be made allocation-free with the bundled runtime. T6 records it.

### T5 — Timing statistics in the diagnostics · M
**Files:** new `core/stats/TimingWindow.kt`; `detector/{PoseEngine,PoseDetector,UltralyticsPoseEngine,
LiteRtPoseDetector,FakePoseDetector}.kt` (`lastPreMs`, `lastPostMs` from the vendored result);
`app/capture/FramePipeline.kt`; `app/diagnostics/{CaptureStats,CaptureStatsHolder,DiagnosticsReport}.kt`;
`TrackerConfig.kt` (window length, thermal sample interval); tests for each.
- `TimingWindow(capacity)`: `add(ms)` allocates nothing; `percentile(p)` works on an internal scratch array
  allocated once; NaN and negative samples are dropped; empty → NaN.
- The pipeline (capture thread) records per processed frame: copy, pre, inference, post, whole frame
  (acquire → publish) and **result age** (publish time − frame timestamp). No new clock: `NanoClock`.
- `summary.txt`: `timingSamples`, and `…MsP50` / `…MsP95` for `copy`, `pre`, `infer`, `post`, `frame`,
  `resultAge`; `thermalStatus` (API 29+, a name or `n/a`) and `thermalHeadroom` (API 30+, sampled no more often
  than the system allows, `n/a` when unknown). Never a guessed number (AGENTS rule 1).
- The HUD text does not change (a changing HUD is captured and feeds back, ARCHITECTURE §6.5).

**Tests first:** window wrap-around, percentiles on known data, dropped samples, empty window; pipeline records
one sample per processed frame with a fake clock and none for drained frames; report lines incl. `n/a`.
